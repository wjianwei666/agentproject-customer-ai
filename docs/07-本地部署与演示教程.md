# 本地部署与演示教程

> 对应交付物 D4
> 适用系统：Windows / macOS / Linux，Python 3.10+

---

## 一、环境要求

| 项 | 要求 | 检查命令 |
|---|---|---|
| Python | ≥ 3.10（推荐 3.11） | `python --version` |
| pip | ≥ 20 | `pip --version` |
| 磁盘 | ≥ 50 MB | — |
| 网络 | **离线可跑**（接真实 LLM 才需要） | — |

---

## 二、安装

```bash
# 1. 进入项目目录
cd 智能客服

# 2. 创建虚拟环境（可选但强烈推荐）
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

# 3. 安装依赖
pip install -r requirements.txt
```

## 三、三种运行方式

### 方式 1：单元测试（验证环境是否正确）

```bash
python -m unittest discover -s tests -v
```

预期输出：`Ran 23 tests ... OK`

### 方式 2：命令行演示（无需 API Key）

```bash
python scripts/demo.py
```

会依次输出三段演示：
1. **基础链路**：6 组典型画像 × 典型意图，展示意图、画像得分、命中规则、知识召回、回复、转人工；
2. **合规门禁**：模拟 LLM 输出违规文案（"全网最低""假一赔十"），观察拦截与整改过程；
3. **结构化输出**：完整的 JSON 响应，可直接对接前端。

### 方式 3：HTTP 服务

```bash
uvicorn src.api:app --host 127.0.0.1 --port 8000 --reload
```

打开 <http://127.0.0.1:8000/docs> 查看交互式 API 文档。

#### 接口清单

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/health` | 健康检查（含 LLM 是否可用、画像数、知识切片数） |
| POST | `/chat` | 主链路 |
| GET | `/personas` | 查看当前生效画像库 |
| POST | `/knowledge/search` | 知识检索排查 |

#### 调用示例

```bash
curl -X POST http://127.0.0.1:8000/chat \
  -H "Content-Type: application/json" \
  -d '{
    "message": "我的快递发货了吗？都五天了还没收到",
    "user": {
      "user_id": "U10003",
      "tags": {"emotion": "anxious", "lifecycle": "active"}
    }
  }'
```

预期结果：
- `intent.intent` = `logistics`
- `persona.persona_id` = `anxious_urgent`
- `knowledge[0].title` = `发货与配送时效` 或 `物流异常处理`
- `need_human` = `false`

## 四、接入真实 LLM（可选）

### 环境变量

```bash
# Windows PowerShell
$env:OPENAI_API_KEY="sk-xxxx"

# macOS / Linux
export OPENAI_API_KEY="sk-xxxx"
```

### 切换模型或网关

编辑 `config/app.yaml`：

```yaml
llm:
  enabled: true
  base_url: "https://api.deepseek.com/v1"   # 换成任意 OpenAI 兼容网关
  model: "deepseek-chat"
  api_key_env: "OPENAI_API_KEY"
  temperature: 0.3
```

**验证是否生效**：`GET /health` 返回 `llm_available: true`。

> 没有 Key 时 `llm_available` 为 false，系统自动走模板生成，**功能完整可用**，
> 这就是离线演示可复现的原因。

## 五、Dify 低代码路线搭建步骤

> 配置文件：`dify/ecommerce_cs_agent.yml`

### 5.1 导入方式

1. 进入 Dify 控制台 → 「工作室」→「创建应用」→「导入 DSL 文件」；
2. 选择 `dify/ecommerce_cs_agent.yml`；
3. **先建知识库**：把 `knowledge/faq.md` 上传为数据集，再把数据集 ID 填进「知识检索」节点的 `dataset_ids`
   （留空会导致 N4 恒为空召回，这是导入后最常见的演示失败原因）；
4. 绑定模型凭据（默认 `gpt-4o-mini`，可换成任意已配置的模型）；
5. 跑一条转人工用例（如「杯子破损，我要投诉」）确认 `need_human = true`。

> 若因 Dify 版本差异导致导入失败，按下面 5.2 在画布手工重建，30 分钟可完成。

### 5.2 手工重建节点清单（18 节点 / 19 条边）

| 顺序 | 节点类型 | 标题（DSL 中 id） | 关键配置 |
|---|---|---|---|
| 1 | 开始 | 开始（`start`） | 变量：`user_message`(文本)、`user_tags`(JSON) |
| 2 | 代码 | 入参脱敏（`code_redact`） | 正则先 18 位证件号、再 11 位手机号，输出 `clean_message` |
| 3 | LLM | 意图识别（`llm_intent`） | System 用 `prompts/01-意图识别.md`，temperature 0，输入 `code_redact.clean_message` |
| 4 | 代码 | 标签人群匹配（`code_persona`） | 粘贴 `prompts/02-标签人群匹配.md` 的 `match_persona`，输出 `persona_id`/`score`/`strategy` |
| 5 | 知识检索 | 知识检索（`kb_retrieval`） | 绑定知识库，TopK=3，score 阈值 0.15 |
| 6 | LLM | 话术生成（`llm_reply`） | System 用 `prompts/03-话术生成.md`，User 用 `prompts/03-话术生成-用户输入.md` |
| 7 | 代码 | 合规质检（`code_guard`） | 正则 block 规则，输入 `llm_reply.text`，输出 `has_block`/`issues`/`block_count` |
| 8 | 条件分支 | 合规分支（`if_compliance`） | `has_block == true` → 整改#1；否则 → 转人工决策 |
| 9 | LLM | 合规整改（`llm_fix`） | System 用 `prompts/04-合规质检.md`，User 为原 reply |
| 10 | 代码 | 合规复查（`code_guard_r2`） | 与节点 7 同一套 block 规则，输入 `llm_fix.text` |
| 11 | 条件分支 | 合规分支-复查（`if_compliance_r2`） | 仍命中 → 整改#2；已通过 → 转人工决策 |
| 12 | LLM | 合规整改-第二轮（`llm_fix_r2`） | 同节点 9，`issues` 取 `code_guard_r2.issues` |
| 13 | 代码 | 本地兜底替换（`code_sanitize`） | 确定性词表替换 + 违规整句删除，兜底文案非空 |
| 14 | 代码 | 转人工决策（`code_handoff`） | 四条件判定，输出 `final_reply`/`need_human`/`handoff_reason` |
| 15 | 条件分支 | 转人工分支（`if_handoff`） | `need_human == true` → 工单；否则 → 结束-自动应答 |
| 16 | 代码 | 工单摘要（`code_ticket`） | 模板拼装 5 要素，输出 `ticket_summary` |
| 17 | 结束 | 结束-自动应答（`end_normal`） | 输出 `reply`/`intent_id`/`need_human`/`handoff_reason` |
| 18 | 结束 | 结束-转人工（`end_handoff`） | 同上 + `ticket_summary`（绑 `code_ticket.ticket_summary`） |

**连线要点**（漏连会直接导致工作流跑不通）：

```
start → code_redact → llm_intent → code_persona → kb_retrieval → llm_reply → code_guard
code_guard → if_compliance
if_compliance --true--> llm_fix → code_guard_r2 → if_compliance_r2
if_compliance_r2 --true--> llm_fix_r2 → code_sanitize → code_handoff
if_compliance_r2 --false--> code_handoff
if_compliance --false--> code_handoff
code_handoff → if_handoff
if_handoff --true--> code_ticket → end_handoff
if_handoff --false--> end_normal
```

> 代码节点返回布尔值时统一用字符串 `"true"`/`"false"`，条件分支用 `contains "true"` 判断，
> 这样在 Dify 0.15.x 与 1.x 上行为一致，不受布尔类型序列化差异影响。

| 输入（模拟 LLM 生成） | 命中规则 | 预期行为 |
|---|---|---|
| 我们是全网最低价 | absolute_wording | block → 整改 |

### 6.3 异常场景样例

| 场景 | 输入 | 预期行为 |
|---|---|---|
| 标签全缺失 | `tags: {}` + "随便聊聊" | 兜底人群 + 转人工（低置信度） |
| 知识无命中 + 高危意图 | `tags: {emotion: angry}` + "你们就是骗子" | 转人工（高危意图无知识） |
| 含隐私信息 | "我的手机 13800001111" | 回复中不含原手机号（已脱敏） |
| LLM 不可用 | 不设 API Key | 模板生成，链路完整 |

## 七、常见问题

| 问题 | 原因 | 解决 |
|---|---|---|
| `ModuleNotFoundError: src` | 未在项目根目录运行 | `cd` 到项目根目录再执行 |
| `yaml` 导入失败 | 未装 PyYAML | `pip install -r requirements.txt` |
| `/chat` 返回 422 | 请求体缺 `user_id` 或 `message` | 按接口文档补齐字段 |
| `llm_available: false` | 未设 `OPENAI_API_KEY` | 设置环境变量，或忽略（离线模式可用） |
| 回复很模板化 | 当前为离线模式 | 接入真实 LLM 后话术会自然很多 |
| Dify 导入报错 | 版本差异 | 按 5.2 手工重建 |
| Windows 控制台中文乱码 | 编码问题 | `chcp 65001` 或设置 `PYTHONUTF8=1` |

### 9.5 关键命令速查

**shot-03｜单元测试**

```bash

       "user": {"user_id": "U10009", "tags": {"emotion": "angry", "value_level": "high"}}}' \
  | jq '{reply, intent: .intent.intent_name, confidence: .intent.confidence,
         persona: .persona.persona_name, score: .persona.score,
         knowledge: [.knowledge[].title], compliance: (.compliance|length),
         need_human, handoff_reason, ticket_summary,
```
