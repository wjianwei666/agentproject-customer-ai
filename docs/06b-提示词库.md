# 提示词库｜电商智能客服 Agent

> 本章对应交付清单第 1 项中的「提示词」与第 3 项的「配套提示词库」。
> 全文与 `prompts/*.md` 同源，变量名与 Dify 节点变量、代码版函数参数**完全一致**，
> 因此同一段提示词可直接复制到 Dify 节点，也可直接落到 `src/` 的 LLM 调用中。

## 一、提示词总览

| 编号 | 提示词 | 所在节点（Dify / 代码版） | 调用时机 | 是否调 LLM | 输出形态 |
|---|---|---|---|---|---|
| P-01 | 意图识别 | N2 `llm_intent` / `src/intent.py::_classify_by_llm` | 规则打分置信度 < 0.6 | 是 | 单个意图 id |
| P-02 | 标签人群匹配 | N3 `code_persona` / `src/tag_matcher.py` | 每次请求 | **否**（规则打分） | 画像 id + 得分 + 策略 |
| P-03 | 话术生成（System） | N5 `llm_reply` / `src/agent.py::_generate_by_llm` | 每次请求 | 是 | 回复正文 |
| P-04 | 话术生成（User 输入） | N5 `llm_reply` 的用户消息 | 与 P-03 同时 | 是 | 用户消息体 |
| P-05 | 合规整改 | N6.5 `llm_fix`、`llm_fix_r2` / `src/agent.py::_revise` | 质检命中 block 级规则 | 是 | 改写后正文 |
| P-06 | 工单摘要 | N8 `code_ticket`（模板版）/ `src/agent.py::_ticket_summary` | `need_human = true` | 可选 | 一行摘要 |

设计原则只有一条：**能用规则的地方不用模型**。P-02 与 P-06 默认走确定性规则/模板，
只有在需要"理解自然语言"的 P-01、P-03、P-05 才调用模型，既控成本又保可复现。

## 二、逐条说明

### 2.1 P-01 意图识别

- **用途**：把用户自然语言收敛到 9 个固定意图之一，作为人群匹配与知识检索的路由键。
- **硬约束**：
  1. 只能输出**唯一**一个意图 id，不得输出解释、标点或 JSON；
  2. 多诉求并存时按优先级链取值：投诉/维权 > 质量问题 > 退换货 > 物流 > 订单 > 价格 > 售前 > 其他；
  3. 无法判断时输出 `other`，不允许自造新意图。
- **关键句式**：

| 句式 | 作用 |
|---|---|
| 「请从下列意图中选择**唯一**最匹配的一个，只输出意图 id」 | 抑制模型输出解释文本，省掉二次解析 |
| 「当用户同时表达多个诉求时，取**情绪最强烈、损失最直接**的那一个」 | 把优先级判断交给模型时给出可执行标准 |
| 「other：其他或闲聊（问候、转人工、无明确诉求）」 | 给模型一个安全出口，避免硬凑分类 |
- **输出示例**：`refund_return`
- **失败兜底**：模型返回不在词表内的字符串时，置信度按 0.30 处理，直接触发转人工。

### 2.2 P-02 标签人群匹配（不调用 LLM）

- **用途**：按 CRM 标签给用户打上画像，并输出该画像的语气、称呼、权益、禁区、收尾动作。
- **为什么不用 LLM**：标签匹配是确定性业务规则，需要可审计、可回滚、可由运营自助改权重；
  人群策略出错会直接造成优惠券超发。
- **规则结构**：

| 要素 | 说明 |
|---|---|
| `field` | 匹配字段：`value_level` / `member_level` / `lifecycle` / `price_sensitivity` / `source` / `service_pref` / `emotion` / `intent` |
| `op` | `equals` / `in` / `not_in` / `contains_any` / `gte` / `lte` |
| `weight` | 命中即累加，取得分最高且 ≥ `match_threshold`（默认 45）的画像 |
- **关键句式（写进策略、直接拼进 P-03）**：

| 句式 | 作用 |
|---|---|
| 「第一句直接给结论，不铺垫」 | 高价值用户反感绕弯，压首句信息密度 |
| 「不要使用"亲""宝子"等泛化称呼」 | 用称呼差异制造身份感 |
| 「不要使用"全网最低""史上最低"等绝对化用语」 | 把合规红线前置到人群策略，减少事后整改 |
- **兜底**：标签缺失 → 该规则判不命中，不做推断；全部不达标 → 回落 `general_fallback`，链路永不中断。

### 2.3 P-03 话术生成（System）

- **用途**：在"人设语气 + 事实边界 + 合规红线"三重约束下生成对客回复。
- **硬约束**：

| 约束 | 具体要求 | 违反后果 |
|---|---|---|
| 人设与语气 | 语气、称呼、沟通重点、权益、收尾全部来自画像策略 | 回复与人群不匹配，体验断层 |
| 事实边界 | 只能用知识片段中的事实，不得编造时效/价格/政策/参数 | 事实性错误，客诉升级 |
| 合规红线 | 无绝对化用语、无超规则赔付、不贬低竞品、不索取隐私、不宣称医疗功效 | 命中 N6 质检，进入整改 |
- **结构要求**：首句结论或共情 → 正文 2-4 句用事实说话 → 末句给明确下一步动作 → 全长 60-180 字。
- **关键句式**：

| 句式 | 作用 |
|---|---|
| 「你的回复必须**同时满足**下面三个约束，缺一即不合格」 | 把软性要求变成硬门禁 |
| 「知识片段中没有的信息，必须回答"我核实后回复您"，并给出下一步动作」 | 给模型一条"不编造"的合法出口 |
| 「优惠力度不得超过 `{{max_discount}}`，超出必须引导至人工客服」 | 把授权上限写进提示词，防止越权让利 |
| 「不要输出任何前缀、标签、JSON 或解释」 | 保证输出可直接下发，无需清洗 |
- **变量注入**：`persona_name` / `tone` / `address` / `focus` / `perks` / `taboos` / `closing` / `max_discount` /
  `intent_name` / `knowledge`，全部由 N3 画像节点与 N4 检索节点产出。

### 2.4 P-04 话术生成（User 输入）

- **用途**：把"用户是谁 + 用户说了什么"装进用户消息体，与 P-03 的 System 分离，便于缓存与调试。
- **硬约束**：`message` 必须使用 **N1 脱敏后**的 `clean_message`，禁止把原始手机号、证件号送进模型。
- **关键句式**：`请按 System 约束生成回复。`——用一句显式指令把模型注意力拉回 System 约束，
  实测可显著降低"忘记人设"的概率。
- **变量注入**：`member_level` / `lifecycle` / `message`（脱敏后）。

### 2.5 P-05 合规整改

- **用途**：质检命中 block 级规则后，对回复做**最小必要改写**，最多 2 轮。
- **硬约束**：
  1. 只删改违规表述，保留事实信息、语气人设与下一步动作；
  2. **不得新增**原文没有的事实（防止模型"越改越编"）；
  3. 绝对化用语改为可验证相对表述，超规则赔付改为"按平台售后规则处理"；
  4. 若某句无法在不违规前提下保留，整句删除。
- **关键句式**：

| 句式 | 作用 |
|---|---|
| 「请**只做最小必要改写**后返回」 | 防止模型重写整段、改变原意 |
| 「**不要新增任何未在原文出现的事实**」 | 整改阶段最常见的事故是"越改越编" |
| 「本次命中的问题：`{{issues}}`」 | 把质检命中的具体词条喂回去，整改命中率显著高于泛泛要求 |
- **闭环**：第 1 轮整改后由 N6 复查节点复检；仍违规则第 2 轮整改；两轮后仍违规，
  走 **N6.9 本地兜底替换**（确定性词表替换 + 违规整句删除），保证**违规内容绝不下发**。

### 2.6 P-06 工单摘要

- **用途**：把会话压缩成坐席可直接接手的一行摘要。
- **硬约束**：不超过 120 字；必须含 5 要素并用「｜」分隔：
  `用户ID｜画像及得分｜意图及置信度｜转人工原因｜建议下一步动作`。
- **关键句式**：

| 句式 | 作用 |
|---|---|
| 「不臆测用户未表达的需求」 | 摘要失真会直接误导坐席 |
| 「不重复用户原话全文，超过 60 字要截断」 | 控制坐席阅读成本 |
| 「原因字段必须与系统给出的 handoff_reason 一致」 | 保证摘要与决策同源，可对账 |
- **实现说明**：代码版与 Dify 版默认用**模板拼装**（`src/agent.py::_ticket_summary`、N8 `code_ticket`），
  零模型成本、零幻觉；如需更自然的表述，可把本段提示词接到 LLM 节点，输出结构不变。

## 三、一次完整调用的提示词实拍

> 下面这条链路把 P-01 ~ P-06 全部走一遍，可直接对照 Dify 工作流日志复现。
> 场景：V4 高价值会员催发货并声称要投诉，用户消息里带了手机号与证件号。

**Step 0｜原始入参（N0 开始节点）**

```text
user_message: 我下单三天了还没发货，再不发货我就去平台投诉了，手机号 13900001111，身份证 110101199001011234
user_tags:    {"user_id": "U10086", "member_level": "V2", "value_level": "high",
               "lifecycle": "active", "emotion": "angry", "source": "private"}
```

**Step 1｜N1 入参脱敏（正则，不调模型）**

```text
clean_message: 我下单三天了还没发货，再不发货我就去平台投诉了，手机号【手机号已隐藏】，身份证【证件号已隐藏】
redacted:      true
```

脱敏先于任何模型调用，保证隐私数据不落进模型日志与训练链路。

**Step 2｜N2 意图识别（P-01）**

```text
System: 你是电商客服意图分类器……（P-01 全文）
User:   我下单三天了还没发货，再不发货我就去平台投诉了，手机号【手机号已隐藏】……
模型输出: complaint
```

虽然提到了发货，但"投诉"优先级更高，按优先级链判为 `complaint`。

**Step 3｜N3 标签人群匹配（P-02，规则打分）**

| 画像 | 命中规则 | 得分 |
|---|---|---|
| 愤怒维权型 | `emotion=angry`(45) + `intent in [complaint, quality_issue, refund_return]`(35) + `value_level in [high, medium]`(10) | **90** |
| 高价值忠诚VIP | `value_level=high`(40) + `lifecycle=active`(20)，`member_level=V2` 与 `intent=complaint` 均不命中 | 60 |
| 焦虑催单型 | `emotion=angry` 不命中 + `intent in [logistics, order_query]` 不命中 | 0 |

取分最高且 ≥ 阈值 45 的画像，最终命中 **愤怒维权型（90 分）**，策略：语气"诚恳、低姿态、不辩解、只给方案"，
称呼"您"，禁区"不要反问用户、不要使用'按规定''公司要求'等推责表述"，
收尾"给出工单号与专属处理人，主动告知下一步时间"，优惠上限 0.20。

**Step 4｜N4 知识检索**

```text
召回片段（faq.md「发货与配送时效」「物流异常处理」）：
现货商品在付款后 24 小时内出库……江浙沪皖次日达，其余地区 2-3 天送达……
若物流信息超过 48 小时未更新，可联系客服发起物流查询工单……
```

**Step 5｜N5 话术生成（P-03 + P-04 渲染后）**

```text
System: 你是电商平台的一线智能客服。你的回复必须同时满足下面三个约束，缺一即不合格。
        约束一：人设与语气（来自用户画像）
        - 当前用户画像：愤怒维权型
        - 语气要求：诚恳、低姿态、不辩解、只给方案
        - 称呼方式：您
        - 沟通重点：第一句直接道歉，不解释原因；一次性给完整解决方案；
                    明确责任人与处理时限，消除"没人管"的恐惧
        - 可给权益：全额退款、免费补发、补偿券
        - 收尾动作：给出工单号与专属处理人，主动告知下一步时间
        约束二：事实边界（只能用知识片段中的事实，不得编造时效、价格、政策、参数）
        约束三：合规红线（不使用绝对化用语、不承诺超规则赔付、不贬低竞品、不索取隐私、不宣称医疗功效）
        当前意图：complaint
        知识片段：现货商品在付款后 24 小时内出库……物流信息超过 48 小时未更新可发起物流查询工单……
User:   【用户信息】会员等级：V2　生命周期：active
        【用户原话】我下单三天了还没发货，再不发货我就去平台投诉了，手机号【手机号已隐藏】……
        请按 System 约束生成回复。

模型原始输出（含违规，不能直接下发）：
        非常抱歉让您久等了，我们是全网最低价，发货肯定最快，假一赔十，您放心。
```

**Step 6｜N6 合规质检（规则命中）**

```text
has_block:   true
issues:      绝对化用语(absolute_wording)：命中「全网最低」；超额赔付承诺(over_promise_compensation)：命中「假一赔十」
block_count: 2
```

**Step 7｜N6.5 整改（P-05）**

```text
System: 你是电商平台的合规审核员。下面这段客服回复命中了合规风险，请只做最小必要改写后返回。
        ……本次命中的问题：绝对化用语(absolute_wording)：命中「全网最低」；超额赔付承诺(over_promise_compensation)：命中「假一赔十」
User:   非常抱歉让您久等了，我们是全网最低价，发货肯定最快，假一赔十，您放心。
整改输出: 非常抱歉让您久等了，我们同价位较优，发货已按优先顺序安排，超时按平台售后规则处理。
```

**Step 8｜N6 复查 → 通过**

```text
has_block: false，进入 N7 转人工决策
```

**Step 9｜N7 转人工决策（四条件）**

```text
合规已解决；意图置信度 0.85 ≥ 0.45；知识命中；但画像 = 愤怒维权型
→ need_human: true，handoff_reason: angry_user_escalation
```

**Step 10｜N8 工单摘要（P-06）**

```text
用户U10086｜画像：愤怒维权型(90分)｜意图：complaint(0.85)｜转人工原因：angry_user_escalation｜诉求原文：我下单三天了还没发货，再不发货我就去平台投诉了……｜建议动作：给出工单号与专属处理人，主动告知下一步时间
```

**Step 11｜结束（转人工）**

```text
reply:          非常抱歉，这个问题需要由人工客服为您处理。已为您生成工单，专属客服将在 30 分钟内与您联系……
need_human:     true
handoff_reason: angry_user_escalation
ticket_summary: 见 Step 10
```

这条链路的验收要点：**用户原话里的手机号与证件号没有进入任何模型**、
**违规话术没有下发**、**转人工带了可接手的原因与摘要**。

## 四、提示词维护规范

| 事项 | 规则 |
|---|---|
| 双真相源 | 代码版改 `prompts/*.md` 与 `config/*.yaml`；Dify 版改节点内提示词；两边都改需人工核对一致性 |
| 变量改名 | 必须同步改 Dify 节点变量选择器与 `src/` 调用参数，否则会静默取空值 |
| 改完必跑 | `python -m pytest tests -q`（23 条用例覆盖脱敏、意图、画像、合规、转人工全链路） |
| 版本留痕 | 提示词变更记入本文件与 `prompts/` 对应文件，注明变更原因与影响节点 |
