| 项 | 内容 |
|---|---|
| 产品目标 | 让电商客服的每一句回复都"看人说话"，且说错话前被拦住 |

## 二、核心业务模型

一句话业务模型：

```
一条用户消息进来 → 判断他想要什么（意图）
                → 判断他是谁（标签人群）
                → 找出唯一可信的事实（知识库）
                → 用他听得进去的方式说（话术生成）
                → 检查有没有说错（合规质检）
                → 搞不定就交给人（转人工 + 工单）
```

**关键产品判断（为什么这么设计）**：

| 决策 | 为什么做 | 为什么不换别的做法 |
|---|---|---|
| 意图与人群**分开两个节点** | 意图决定"答什么"，人群决定"怎么说"，混在一起会导致话术被意图绑架 | 用一个大模型一次搞定，不可解释、不可调参、成本高 |
| 人群匹配用**规则打分**而非模型 | 运营要能随时改权重，且优惠券超发必须可审计 | 用 LLM 分类不可复现，出错无法回滚 |
| 知识库**独立于话术生成** | 事实与表达分离，避免模型编造时效和价格 | 让模型直接答，幻觉成本高于收益 |
| 合规质检做成**独立节点** | 这是商家的付费理由，必须能被统计、被展示 | 写在提示词里，无法拦截、无法出报表 |
| 必须有**兜底人群** | 中小商家标签残缺是常态 | 无兜底会导致链路中断，客服直接不可用 |

## 三、产品模块架构

```
┌─────────────────────────────────────────────────────────┐
│                     接入层                               │
│   网页客服组件 / 小程序 / 企微 / 平台店铺消息  →  统一 API │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│                   Agent 编排层（6 节点）                  │
│  ①脱敏 ②意图识别 ③标签人群匹配 ④知识检索                  │
│  ⑤话术生成 ⑥合规质检 → 转人工决策                         │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│                    能力支撑层                            │
│  标签中心 │ 知识库 │ 提示词库 │ 合规规则库 │ 画像库        │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│                    运营配置层                            │
│  人群策略配置 │ 意图关键词配置 │ 合规规则配置 │ 效果看板   │
└─────────────────────────────────────────────────────────┘
```

**模块边界说明（哪些不做）**：

| 不属于本产品 | 归属 |
|---|---|
| 全渠道消息网关 | 商家已有客服系统 |
| 坐席工作台 / 排班 | 商家已有客服系统 |
| 商品主数据管理 | 商家 ERP / 商品中台 |
| 订单与物流实时查询 | 需通过 HTTP 工具对接商家 OMS（二期） |
| 营销触达（短信/推送） | 商家已有 SCRM |

## 四、用户主流程

### 4.1 买家侧主流程

```
用户发起会话
   ↓
[自动] 携带 user_id 与标签入参（前端从登录态取，缺失则为空）
   ↓
① 脱敏：手机号/证件号不进入链路
   ↓
② 意图识别 ──低置信度──→ 转人工
   ↓
③ 标签人群匹配 ──无匹配──→ 兜底人群（继续服务，不中断）
   ↓
④ 知识检索 ──无命中 + 高危意图──→ 转人工
   ↓
⑤ 话术生成（按人群语气）
   ↓
⑥ 合规质检 ──命中 block──→ 整改重试 2 轮 ──仍失败──→ 本地兜底替换
   ↓
输出回复 + （如需）转人工按钮 + 工单摘要
```

### 4.2 运营侧配置流程

```
登录后台 → 选择店铺 → 配置 4 类策略 → 保存生效（无需研发介入）
  ├─ 人群策略：7 个画像的规则权重、语气、称呼、权益上限、表达禁区
  ├─ 意图关键词：8 类意图的关键词与权重
  ├─ 合规规则：block/warn 规则与整改文案
  └─ 知识库：上传政策/商品文档（按标题切片）
```

### 4.3 异常场景设计

| 异常 | 系统行为 | 用户感知 |
|---|---|---|
| 用户无任何标签 | 走兜底人群，正常回复 | 无感知 |
| 用户情绪愤怒 | 直接转人工 + 工单摘要 | 看到"已安排专人" |
| 知识库无命中 | 不编造，回复"核实后答复" + 记录待办 | 看到确定性承诺 |
| 合规整改失败 | 本地规则替换后下发 | 看到合规文案 |
| LLM 服务不可用 | 自动降级为模板生成 | 回复稍模板化但可用 |
| 同一会话连续 3 次未解决 | 强制转人工 | 看到转人工入口 |

## 五、功能清单（MoSCoW + 优先级）

### Must have（一期，P0）

| 编号 | 功能 | 说明 | 验收标准 |
|---|---|---|---|
| F01 | 意图识别 | 8 类意图 + 置信度 | 黄金集准确率 ≥ 90% |
| F02 | 标签人群匹配 | 7 维标签 + 7 个画像 + 兜底 | 命中率可解释，无标签不报错 |
| F03 | 知识检索 | 标题切片 + BM25 召回 | Top1 命中率 ≥ 85% |
| F04 | 差异化话术生成 | 按人群语气/称呼/禁区生成 | 盲评"像人说的" ≥ 4 分（5 分制） |
| F05 | 合规质检 | block/warn 两级 + 整改 | block 违规零下发 |
| F06 | 转人工与工单摘要 | 4 类触发条件 | 摘要含 5 要素 |
| F07 | 结构化 API | 单次请求返回完整 trace | 可被前端直接消费 |

### Should have（二期，P1）

| 编号 | 功能 | 说明 |
|---|---|---|
| F08 | 多轮上下文 | 保留最近 3 轮意图与已给方案 |
| F09 | 订单/物流实时查询工具 | HTTP 工具节点对接商家 OMS |
| F10 | 效果看板 | 转人工率、拦截条数、人群分布 |
| F11 | 人群策略 A/B 测试 | 同店铺分流对比 |

### Could have（三期，P2）

| 编号 | 功能 | 说明 |
|---|---|---|
| F12 | 向量检索升级 | 知识量 > 5000 chunk 时切换 |
| F13 | 主动跟进 | 未解决会话 24h 后自动回访 |
| F14 | 话术自动优化 | 基于人工改写记录做提示词迭代 |

### Won't have（明确不做）

语音客服、多语言、客服坐席工作台、营销触达、商品主数据管理。

## 六、版本规划

| 版本 | 周期 | 范围 | 里程碑 |
|---|---|---|---|
| V1.0 MVP | 第 1-2 周 | F01-F07 | 链路跑通 + 23 条单测全绿 + Dify 工作流可演示 |
| V1.1 | 第 3-4 周 | 黄金评测集 30 条 + 策略配置后台（表单化） | 通过率 ≥ 90% |
| V1.2 | 第 5-6 周 | 3 家标杆商家试点 + 数据埋点 | 转人工率下降 ≥ 15% |
| V2.0 | 第 7-10 周 | F08-F11 | 看板与 A/B 上线 |
| V3.0 | 第 11 周+ | F12-F14 | 检索升级与自动优化 |

**灰度方案**：先按 10% 会话分流，观察 48 小时；合规拦截条数与人工改写率无异常再放到 50% → 100%。

## 七、核心指标体系

| 层级 | 指标 | 定义 | V1 目标 |
|---|---|---|---|
| 北极星 | 有效解决率 | 未转人工且用户未二次追问的会话占比 | ≥ 65% |
| 质量 | 意图识别准确率 | 黄金集正确数 / 总数 | ≥ 90% |
| 质量 | 知识 Top1 命中率 | 首位召回即正确答案占比 | ≥ 85% |
| 质量 | 合规拦截率 | 被拦截会话 / 生成含风险会话 | 100%（block） |
| 质量 | 话术人工改写率 | 坐席接手后重写比例 | ≤ 20% |
| 效率 | 首响时长 | 请求到回复 | ≤ 800ms（不含 LLM） |
| 效率 | 转人工率 | 转人工会话 / 总会话 | 相对下降 ≥ 15% |
| 成本 | 单会话 LLM 成本 | token 折算 | ≤ 0.02 元 |
| 体验 | 满意度 | 会话结束评分 | ≥ 4.2（5 分制） |

**关键埋点**：`intent_id`、`intent_confidence`、`persona_id`、`persona_score`、`knowledge_top1_score`、
`compliance_block_count`、`compliance_retry`、`need_human`、`handoff_reason`、`elapsed_ms`。

## 八、产品风险与取舍说明

| 风险 | 取舍 | 说明 |
|---|---|---|
| 人群策略太复杂，运营学不会 | 一期只暴露「权重 + 语气 + 称呼 + 权益上限 + 禁区」5 个可调项 | 其余写死，降低配置成本 |
| 画像过多导致维护成本高 | 一期 7 个画像封顶，新增画像需走评审 | 画像膨胀会让策略互相打架 |
| 合规规则误杀正常话术 | block 只放最确定的 5 类，其余降为 warn | 误杀比漏放的体验损失更大 |
| 话术长度失控 | 硬约束 60-180 字 | 客服场景长文等于不专业 |
| 依赖 LLM 导致不可用 | 默认离线模板可跑通全链路 | 演示与试点不依赖外部服务 |

**明确不做的事**：不追求"什么都能答"，追求"答的一定对、一定合规、一定像人说的"。
