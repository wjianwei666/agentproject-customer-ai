## 二、技术选型对比

| 维度 | 方案 A：Dify 低代码 | 方案 B：本地代码版 | 结论 |
|---|---|---|---|
| 交付速度 | 快（画布拖拽，1-2 天搭完） | 中（3-5 天） | A 优 |
| 可视化演示 | 强（工作流可直接展示给客户） | 弱（只能跑命令行） | A 优 |
| 可调试性 | 中（依赖平台日志） | 强（可断点、可单测） | B 优 |
| 二次开发 | 弱（受平台能力限制） | 强（完全可控） | B 优 |
| 部署成本 | 需部署 Dify 服务（4C8G 起） | 单进程 2C4G 足够 | B 优 |
| 私有化 | 中（需部署整套 Dify） | 强（一个 Python 进程） | B 优 |
| 成本 | Dify 开源免费 + LLM 费用 | 仅 LLM 费用 | B 略优 |

**最终决策：双路线并行，共用同一套资产。**

```
config/*.yaml   +   prompts/*.md        ← 两条路线共用（策略与提示词唯一真相源）
        │
        ├──→ dify/ecommerce_cs_agent.yml   （Dify 工作流，交付与演示）
        └──→ src/                          （代码版，私有化与兜底）
```

这样做的关键收益：**改策略只需改 YAML，两条路线同时生效，不会出现"演示版和交付版话术不一致"**。

### 技术栈明细

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.11 | 与 Dify 代码节点一致，一套逻辑两处复用 |
| HTTP 框架 | FastAPI + Uvicorn | 自带 OpenAPI 文档，前端联调零成本 |
| 数据校验 | Pydantic v2 | 接口契约强约束，避免字段漂移 |
| 配置 | YAML | 运营可读可改，无需研发介入 |
| 检索 | 自研 BM25（字级 n-gram） | 零依赖、可解释；100-500 chunk 量级够用 |
| LLM | OpenAI 兼容协议（urllib 直连） | 不锁 SDK 版本，可无缝切 DeepSeek/通义 |
| 测试 | 标准库 unittest | 无第三方测试依赖，任何机器可跑 |
| 部署 | 单进程 + Nginx 反代 | 一期无需容器编排 |

**明确不引入**：向量数据库、消息队列、Redis、K8s。理由：一期并发 20 QPS，引入即是负债。

## 三、系统架构

### 3.1 部署架构

```
              ┌──────────────┐
   买家侧 ───→│  Nginx / CDN │
              └──────┬───────┘
                     ▼
        ┌────────────────────────────┐
        │   FastAPI (uvicorn, 2 workers)│
        │  ┌──────────────────────┐  │
        │  │ EcommerceCSAgent     │  │
        │  │  ├ IntentClassifier  │  │
        │  │  ├ PersonaMatcher    │  │
        │  │  ├ KnowledgeRetriever│  │
        │  │  ├ ComplianceChecker │  │
        │  │  └ LLMClient(可选)    │  │
        │  └──────────────────────┘  │
        └───────┬────────────┬───────┘
                │            │
      ┌─────────▼──┐   ┌─────▼──────────┐
      │ 本地文件资产 │   │ LLM API(可选)   │
      │ config/     │   │ OpenAI 兼容网关 │
      │ knowledge/  │   └────────────────┘
      │ prompts/    │
      └─────────────┘
```

### 3.2 请求链路（单次 /chat）

```
POST /chat
  → Pydantic 校验（ChatRequest）
  → redact 脱敏                       ≈ 0.1ms
  → IntentClassifier.classify         ≈ 0.5ms（规则）
  → PersonaMatcher.match              ≈ 0.1ms
  → KnowledgeRetriever.search         ≈ 1ms（BM25）
  → 话术生成（模板 / LLM）             ≈ 0.5ms / 800-2000ms
  → ComplianceChecker.check           ≈ 0.2ms
  → 转人工决策 + 工单摘要              ≈ 0.1ms
  → 返回 ChatResponse（含 trace）
```

**离线模式端到端 < 5ms**，这是"合规质检不拖慢响应"的技术依据。

## 四、核心模块拆解

| 模块 | 文件 | 职责 | 关键设计 |
|---|---|---|---|
| 数据契约 | `src/models.py` | 定义 7 个模型，Dify 与代码版字段对齐 | trace 字段贯穿全链路，可观测 |
| 配置加载 | `src/config_loader.py` | 加载 YAML + 提示词模板渲染 | 缓存 + 极简 `{{var}}` 替换，不引 jinja2 |
| 意图识别 | `src/intent.py` | 关键词打分 → 低置信度时 LLM 兜底 | 规则优先控成本；长词加权防短词抢占 |
| 人群匹配 | `src/tag_matcher.py` | 7 维标签规则打分，取最高分画像 | 标签缺失即跳过，绝不推断 |
| 知识检索 | `src/retrieval.py` | Markdown 按 `##` 切片 + BM25 | 中文 1-gram + 2-gram，无需分词器 |
| 合规质检 | `src/compliance.py` | 正则规则匹配 + 本地兜底替换 | block/warn 两级，三重防线 |
| LLM 客户端 | `src/llm.py` | OpenAI 兼容调用 + 离线降级 | 任何异常不抛给用户 |
| 编排器 | `src/agent.py` | 6 节点串联 + 整改闭环 + 转人工 | 单函数分步，业务方可读 |
| 接口层 | `src/api.py` | /chat /health /personas /knowledge/search | 暴露降级状态便于运维 |

### 关键实现细节（研发必读）

1. **脱敏顺序**：必须先替换 18 位证件号，再替换 11 位手机号，否则证件号会被手机号规则截断。
2. **YAML 陷阱**：`315` 这类关键词会被 YAML 解析成整数，代码里统一 `str()` 转换。
3. **合规闭环**：`生成 → 质检 → LLM 整改（最多 2 轮）→ 本地兜底替换 → 再质检`，
   任一步通过即下发，绝不把 block 级文案发给用户。
4. **降级策略**：`LLMClient.available == False` 时自动走模板生成，链路完整可用。

## 五、数据设计

一期无需数据库，用户画像由调用方以 JSON 传入。若需持久化，建议如下最小表结构：

```sql
-- 用户画像表（可选，一期由上游 CRM 直接传入）
CREATE TABLE user_profile (
  user_id        VARCHAR(64) PRIMARY KEY,
  lifecycle      VARCHAR(16),   -- new/active/silent/churn_risk
  value_level    VARCHAR(16),   -- high/medium/low
  price_sensitivity VARCHAR(16),-- sensitive/neutral/insensitive
  member_level   VARCHAR(8),    -- V0-V5
  source         VARCHAR(16),   -- live/search/private/content
  service_pref   VARCHAR(16),   -- self_service/human/community
  emotion        VARCHAR(16),   -- anxious/angry/rational
  updated_at     TIMESTAMP
);

-- 会话与拦截记录表（用于效果看板，二期）
CREATE TABLE session_log (
  id             BIGINT PRIMARY KEY,
  session_id     VARCHAR(64),
  user_id        VARCHAR(64),
  intent_id      VARCHAR(32),
  intent_conf    DECIMAL(4,3),
  persona_id     VARCHAR(32),
  persona_score  DECIMAL(6,2),
  top1_kb_score  DECIMAL(4,3),
  block_count    INT,
  compliance_retry INT,
  need_human     BOOLEAN,
  handoff_reason VARCHAR(32),
  elapsed_ms     DECIMAL(8,2),
  created_at     TIMESTAMP
);
CREATE INDEX idx_session_log_created ON session_log(created_at);
CREATE INDEX idx_session_log_persona ON session_log(persona_id);
```

**知识库存储**：一期直接读 `knowledge/*.md`，按 `## 标题` 切片。
升级向量检索时，仅需替换 `KnowledgeRetriever.search` 的实现，接口不变。

## 七、技术风险与应对

| 风险 | 等级 | 影响 | 应对 |
|---|---|---|---|
| 中文 BM25 无分词导致召回差 | 中 | Top1 命中率低 | 已用字级 1-gram + 2-gram 缓解；上线后用黄金集验证，不达标切 jieba 或向量 |
| LLM 输出不稳定 | 中 | 话术风格漂移 | temperature 0.3 + 严格 System 约束 + 合规兜底 |
| Dify DSL 版本不兼容 | 低 | 导入失败 | 提供节点清单，30 分钟内可重建画布 |
| 合规规则误杀 | 中 | 正常话术被拦 | block 仅 5 类最确定规则，其余 warn；上线后统计误杀率 |
| 长会话 token 成本失控 | 低 | 成本超预算 | 一期无多轮记忆，单次请求独立计费 |
| 并发不足 | 低 | 20 QPS 以上瓶颈 | 检索为纯内存计算，扩容只需加 worker |

## 八、部署与运维方案

### 环境划分

| 环境 | 用途 | 配置 |
|---|---|---|
| dev | 本地开发 | 单进程 + `--reload` |
| test | 联调与评测 | 单进程 + 黄金评测集 |
| prod | 商家试点 | 2 workers + Nginx 反代 + 日志切割 |

### 启动方式

```bash
pip install -r requirements.txt
uvicorn src.api:app --host 0.0.0.0 --port 8000 --workers 2
```

### 监控要点

| 指标 | 阈值 | 动作 |
|---|---|---|
| `/health` 中 `llm_available` | 变 false | 告警：已降级为模板模式 |
| `elapsed_ms` P99 | > 3000ms | 检查 LLM 网关 |
| `need_human` 占比 | > 35% | 检查知识库与意图配置 |
| `block_count > 0` 占比 | > 5% | 检查提示词，可能被注入 |
| 接口 5xx 率 | > 0.5% | 回滚上一版本 |

### 灰度与回滚

- 灰度：按 `user_id` 哈希分流 10% → 50% → 100%；
- 回滚：配置与提示词均为文件，回滚只需还原 YAML/MD 并重启（< 1 分钟）；
- 数据安全：默认不落盘会话原文，`session_log` 只存结构化指标。
